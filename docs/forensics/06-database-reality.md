## 1. MongoDB Database Reality (Authoritative Store)

The API server connects to MongoDB via Mongoose. All durable business records, auth sessions, campaign queues, execution states, and audit records reside in MongoDB collections.

### 1.1 Identity Convention
- **ID Format:** Exact canonical UUIDv4 strings generated by `generateEntityId()` (`@leadforge/schema`).
- **Mongoose `_id` Definition:** Explicitly typed as `{ _id: { type: String, default: generateEntityId } }`.
- **Foreign Key References:** Direct string matching (e.g. `companyId`, `workspaceId`, `contactId`, `campaignId`).
- **Parity:** `MongoDB._id === API.id === SQLite.id`.

## 3. Database Reality Findings

1. **MongoDB is the True Authoritative Store:** All mutations that originate from the API or worker plugins persist directly into MongoDB.
2. **SQLite is Structurally Disposable:** The SQLite cache schema has zero legacy `sync_queue` tables and zero `syncStatus` dirty flags. It can be deleted (`rm leadforge_<wsId>.db`) and cleanly regenerated on startup without data loss.
3. **Hydration Dependency:** Because SQLite is the sole data source queried by the desktop renderer (`companies:query`, `contacts:query`), any failure in `CacheHydrator` immediately results in an empty UI despite MongoDB having full data.
